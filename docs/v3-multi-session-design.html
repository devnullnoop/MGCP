MGCP v3 — Multi-Session

One store, many sessions, without silent loss. Three independent workstreams: remove the single-writer lock, stop paying for the embedding model once per process, and make concurrent writes fail loudly instead of quietly. Every number below is measured on this machine, not estimated, unless it says otherwise.

The resource story is the opposite of the intuition: the vectors are trivial and the model is the cost. Correction, measured 2026-10-01: the guess below that a Qdrant daemon would be "noise" was wrong — it idles at 474.9 MiB for 656K of stored data, about the same as one MGCP process. Server mode buys correctness at roughly one extra process of memory, which is a real trade rather than a free one. Concurrency is therefore cheap to make correct and expensive to make efficient, and those are different pieces of work.

Workstream A — Qdrant server mode

The smallest of the three, and already half-designed: both store docstrings document Server mode: QdrantClient(host="localhost", port=6333) while the code only ever calls QdrantClient(path=...). qdrant-client 1.16.2 supports url, host, port, api_key and prefer_grpc already.

MGCP does not require a server, a daemon or a container. Embedded is the default and the single-session path: nothing to install, nothing to run, no Docker. Server mode exists only for the operator who wants concurrent sessions, and how the server is run is entirely their choice — a native binary, a managed service, a remote instance. Docker was used once, to obtain a real Qdrant to verify against, and is not part of the project.

Design

  • One resolver, qdrant_client_args(), returns either {"path": ...} or {"url": ..., "api_key": ...} from MGCP_QDRANT_URL (and MGCP_QDRANT_API_KEY). Three construction sites change: qdrant_vector_store.py:71, qdrant_catalogue_store.py:74, server.py:123.
  • Embedded stays the default. A single-session user should never have to run a daemon. Server mode is opt-in by setting the URL.
  • mgcp-init gains --qdrant-url, writes it into the client env block, and mgcp-doctor-style verification pings /readyz.
  • A migration path: mgcp-migrate already rebuilds the Qdrant index from SQLite, which is the embedded→server migration. It needs no new code, only documentation — point it at the server and re-index. SQLite remains the source of truth, so this is reversible.
  • Collection names, vector size (768) and distance (Cosine) are unchanged, so vectors are bit-identical across modes.

Workstream B — shared embedding

embedding.py is already a single @lru_cache(maxsize=1) instance — per process. The work is to make the cache process-wide rather than per-interpreter, without changing the vectors.

Why a daemon and not Qdrant's own inference

Qdrant can embed server-side via FastEmbed, which looks like the tidier answer. It is rejected: it changes which model produces the vectors, so the entire corpus would need re-embedding, and the retrieval-quality baseline measured over nine months (median top-1 0.691) would no longer be comparable. Keeping BGE exactly as it is means the vectors, the scores and every number in the Signal view stay continuous across the upgrade.

Design

  • A small daemon exposing embed / embed_query / embed_batch over a unix domain socket in ~/.mgcp/ — not TCP, so it is not reachable off-box and needs no auth.
  • embedding.py keeps its current signatures and gains a client path: if the socket exists, use it; otherwise load the model in-process exactly as now. No caller changes.
  • Lazy start: the first client that finds no socket spawns the daemon and waits for readiness. Idle timeout shuts it down, so a one-off CLI does not leave 400 MB resident.
  • Correctness gate: a test asserts in-process and over-socket embeddings are identical for the same input, so the two paths can never drift.

Latency. A socket round trip adds roughly 1–3 ms (unmeasured — to be confirmed before committing to this). Observed retrieval latency today is 40–260 ms, so the overhead should be well inside noise. If measurement contradicts that, B is droppable without affecting A or C.

Workstream C — writes that fail loudly

The one that matters most, because its failure mode is invisible. Two halves: detect the conflict, and stop manufacturing conflicts that need not exist.

  • lessons.version and workflows.version exist already. Project contexts need a revision INTEGER NOT NULL DEFAULT 0, added by the same idempotent migration pattern used for rem_state and context_history.
  • The MCP tools surface the conflict as a message the agent can act on: what changed, and that it should re-read. An agent retrying after a re-read is correct behaviour; an agent silently overwriting is not.
  • JSON configs get the same treatment via mtime+hash CAS, plus atomic os.replace so a torn read is impossible.

C2 — narrow writes

Most conflicts today are manufactured. save_project_context takes a whole object when the caller means "append a decision" or "set notes", so two sessions editing unrelated fields collide for no reason. Adding field-scoped operations removes the conflict instead of detecting it:

save_project_context stays for the session-close path that genuinely writes everything, but it becomes the exception rather than the only tool.

The ordering is the one firm recommendation in this document. A before C would make the data-loss window wider at exactly the moment more writers appear.

Risks

  • CAS surfaces conflicts to an agent that may handle them badly. A retry loop that re-reads and blindly re-applies is just last-writer-wins with extra steps. The tool message must say what changed, and REM's existing interactive-review path is where genuine merges belong.
  • A daemon that must be running is a new failure mode. Both A and B must degrade to embedded/in-process when their daemon is absent, and say so, rather than failing the call.
  • Migration is a re-index, and re-indexing is where corpora get lost. mgcp-migrate must refuse to start without a verified backup, and the embedded store must be left intact until the server copy is checksum-verified.
  • Two write paths during transition. While both embedded and server modes exist, a misconfigured second session could write to the other store. The resolver must be the single source of that decision, and /api/health should report which mode is live.

Explicitly out of scope

  • A write broker or queue. CAS covers the realistic contention for a single operator with a few sessions. A broker is the answer to a problem no measurement here supports.
  • Human review of every write. The value of MGCP is that capture is cheap and automatic; gating it on approval would destroy that. Review belongs where REM already puts it: destructive consolidation.
  • Multi-user / remote access. Unix socket and localhost only. No auth story, no network exposure, no tenancy.
  • Changing the embedding model. Nine months of scores depend on BGE producing the same vectors.

Open questions

  1. Does the socket round trip actually cost 1–3 ms? Measure before committing to B.
  2. Should the Qdrant server be managed by MGCP (spawn/supervise) or by the operator (a native binary, a managed service, a remote instance)? Managed is friendlier; unmanaged is honest about what it is. Either way it stays optional.
  3. On a CAS conflict in refine_lesson, is the right default to retry once automatically after a re-read, or to always hand the conflict to the agent?
  4. Does context_history's per-session upsert need CAS too, or is last-write-of-a-session genuinely the intent? (Current belief: intent, no CAS.)
