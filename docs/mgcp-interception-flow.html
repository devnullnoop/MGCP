MGCP Interception Flow

How MGCP actually intervenes in a session: which hooks fire, which one can refuse a tool call, what state flows between them, and what is recorded. Regenerated from the code at hook template v2.13 — the previous version of this document described v2.4 and predated the apology gate entirely, so it was rebuilt rather than patched.

1. Five hooks, one of which can say no

Four hooks inject text into <system-reminder> tags that the model may read or skim. Only pre-tool-dispatcher.py returns permissionDecision: "deny", which the harness obeys.

2. The one enforcing path

Two independent mechanisms live in this hook. Data rules are JSON and match on tool arguments; the apology gate is built in because its trigger is the assistant's own text, not a tool argument. Either can deny. The hook fails open on any parse error — enforcement is a net, not a tripwire.

DISCOVERY_TOOLS is {ToolSearch, ListMcpResourcesTool, ReadMcpResourceTool}. Exempting them is the deadlock fix: in a harness that loads tool schemas on demand, reaching add_lesson requires a discovery call, and gating that locked the agent in a room with the key inside.

Trigger and precondition vocabulary

Trigger command_match.typePrecondition type
git_subcommand, regex, contains tool_called_this_turn, tool_not_called_this_turn, staged_files_coupling, tool_input_glob

Bash commands are tokenised per line with shlex(punctuation_chars=True) — per line because a newline separates commands and shlex otherwise eats it. Git's global flags are skipped, so git -C /path commit is still a commit. A line that cannot be tokenised (an apostrophe in a commit message) falls back to a raw boundary scan and fails closed for git only: a command the detector cannot read is not evidence the command is safe.

The seven apology patterns are word-boundary regexes over the current turn's assistant text: sorry, my bad, you're right, you are right, my mistake, my apology/apologies, apologize/apologise. Keyword, not semantic — a semantic tier was measured and rejected.

3. Per-turn state — one file

Everything flows through ~/.mgcp/workflow_state.json (overridable with MGCP_STATE_FILE / MGCP_DATA_DIR). Until v2.13 the MCP tools wrote a second file, reminder_state.json, that no hook has ever read — so schedule_reminder and update_workflow_state were inert for months. One file now.

The file is shared across concurrent sessions, so an adjudication is scoped by turn_session_id and the PreToolUse gate requires an exact match. Anything that rewrites this file wholesale — reset_state once did — drops the per-turn enforcement keys mid-turn, re-shutting the gate and failing every tool_called_this_turn precondition. It merges now.

4. What gets recorded

~/.mgcp/gate_audit.jsonl is append-only and records friction, not traffic: allowed calls leave no entry.

EventCarriesMeaning
denygate (rules|apology), tool_denied, rules, session_idA tool call was refused
complylesson_idThe apology gate was satisfied by writing a lesson
adjudicationverdict, flagged_sentence, reasoningThe fire was contested or confirmed on the record
human_bypassscopesA human typed MGCP_BYPASS

Known gap: an apology deny does not record the sentence that triggered it — only an adjudication does. So the gate's false-positive rate cannot be measured unless the model volunteers a contest.

5. Retrieval — two paths into context

query_lessons returns direct semantic matches, then optionally bridges through a matching community summary to surface neighbours the direct search missed.

flowchart TB Q[task_description] --> S["vector_store.search
direct semantic match"] S --> D[direct hits, scored] Q --> CS["query_community_summaries"] CS --> C{"community score >= 0.5?"} C -->|no| OUT C -->|yes| MEM[members not already direct hits] MEM --> SC["score each member
against the query"] SC --> F{"score >= BRIDGE_MIN_SCORE?"} F -->|no| DROP[dropped] F -->|yes| TOP[top 3 by score] D --> OUT[response + telemetry] TOP --> OUT

v2.13 fix. The bridge used to rank candidates by usage_count and then call record_usage on whatever it appended — ranking by the number it wrote. Measured over 7,397 retrieved slots: 31.8% arrived through the bridge logged as score 0.0, 66% of those went to three lessons, and ~30 lessons had never surfaced once. Candidates are now ranked by their own similarity to the query, floored, logged with real scores, and the bridge no longer writes the signal it reads.

6. REM — per-project cadence, global corpus

When a cycle is due follows the triggering project's own session count; what it maintains is the whole shared store. rem_state is keyed (project_id, operation) so one project's run cannot silence another's clock.

session, last_run)?"} ID -->|no| SKIP[skipped] ID -->|yes| RUN[run operation] RUN --> F[findings returned to the caller] RUN --> ST[("rem_state
(project_id, operation)")] ST -->|next_due_session| SI["SessionStart warns when overdue"] F -.->|"only finding_count is persisted"| ST

Six operations ship: staleness_scan, duplicate_detection, community_detection, knowledge_extraction, intent_calibration, gate_audit_review. Findings themselves are not stored — only {"finding_count": N} — so rem_report shows schedule state and counts, not the findings of a past cycle.

Qdrant runs in local mode, which permits one client per path. A second MGCP process therefore cannot open the store, and every vector-backed tool in it fails. The dashboard works around this by opening Qdrant only when a route actually needs it — every analytics view reads SQLite and the audit log, so it runs read-only beside a live MCP server, and only lesson writes return 503. That is a mitigation, not a fix: concurrent sessions still contend, which is what Qdrant server mode would resolve.

8. Remaining gaps

Apology denials are unattributed. The flagged sentence is recorded only when contested, so false-positive rate is unmeasurable from the log alone.

The git gate can become unsatisfiable. git-requires-query-lessons demands query_lessons in the same turn, but query_lessons fails outright when another process holds the Qdrant lock — so the precondition cannot be met and commits are blocked for a reason unrelated to git.

Four of seven live rules have never fired. Two rules account for 89 of 92 rule-denials. A rule that never fires is either dead or mis-triggered, and the log cannot tell you which.

Advisory hooks remain advisory. Everything except PreToolUse is text the model may ignore; the enforcement layer covers tool calls, not reasoning.
